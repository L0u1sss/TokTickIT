## Reflection

The agent was most useful when the request named exact PRs and supplied reviewer feedback, because each recommendation could be checked against concrete lines instead of accepted blindly. Several corrections required judgment rather than copying a reference: retaining the approved ticket-number format, separating Lab 2 requirements from optional production hardening, preserving supported legacy database rows through a corrective migration instead of rewriting applied migration history, treating requester selection as pending until Continue commits a revalidated ID, and keeping attachment upload out of the Create Ticket transaction because the approved contract requires an existing Ticket ID. The first database-test run exposed an assertion that expected a named check even though PostgreSQL rejected the oversized varchar earlier; the test was corrected to verify both enforcement layers. Issue #15 reinforced that a disabled submit button alone is insufficient: the UI reuses one UUID after an uncertain outcome while the server and database return the original Ticket for an identical replay. Issue #16 similarly showed why mocked component checks alone were insufficient: a disposable PostgreSQL fixture was added to prove requester-first counting, stable tie-breaking, combined filters, active-attachment counts, and beyond-last-page behavior against the real schema. The PR #24 follow-up also showed why review comments should be verified against the source of truth: the sort contract was already aligned, while silent URL fallback and indistinguishable metadata failure were genuine gaps that required code, contract, and test changes. The author should review the final diff and obtain real-browser responsive evidence, hosted CI, and peer re-review before merge.
